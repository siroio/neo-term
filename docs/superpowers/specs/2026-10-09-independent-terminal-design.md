# neo-term独自端末エンジンへの移行

## 目的と制約

ユーザーは通常のターミナルと同程度の入力感を要求し、libvtermを使用しないよう指定した。neo-termがConPTYから受け取るVTストリームを独自に解析し、端末画面・カーソル・履歴・キー変換を管理する。実装やバイナリへのlibvtermの組み込みを終了する。追加指定に従い、Vimを起動する検証を外し、実際のEmacsの入力・描画・コピー・リサイズで検証する。

対象は現在のWindows x64、ConPTY、Emacs動的モジュールの構成。ConPTYはWindowsのCLIを動かすOSインターフェースとして維持する。現行機能を理由なく削除しない。コミット、push、インストール済みパッケージの変更はこの作業に含めない。

## 採用する構成

ConPTYの入出力とプロセス管理は既存のnative/conpty.cppに残す。libvtermの呼び出しを、neo-term所有のC++端末エンジンに置き換える。外部ライブラリのソースをコピーして名前だけ変える移行は行わない。

エンジンを次の責務に分ける。

- ストリーム解析：分割されたUTF-8、C0、ESC、CSI、OSCを状態機械で解析する。読取境界をまたぐ文字と制御列を保持する。
- 画面管理：主画面・代替画面、カーソル、セル属性、スクロール領域、編集・消去、行の継続情報を保持する。
- 入力変換：カーソルキー、修飾キー、ファンクションキー、bracketed paste、マウス報告を端末モードに合わせて符号化する。
- Unicode：Unicode公式データから生成した独自の幅・結合文字テーブルを使用する。全角セルと結合文字をセル単位で保持する。

既存のScreen/CellとScreenEncoderの通信契約を維持し、Emacs側にVT解析を移さない。更新された行だけを通知・描画し、カーソルのみの移動で文字を再挿入しない。解析時に変更行を記録し、snapshotとJSON化ではその行だけを扱う。全セルを走査してから差分を判定しない。

## 既存機能の移行

SGRの色・背景・太字・斜体・下線・反転を保持する。カーソル位置・表示・形状・点滅、保存/復元、スクロール、文字/行の挿入と削除、画面と行の消去、タブ、オートラップ、原点モード、代替画面を扱う。端末状態やカーソル位置の問い合わせに応答する。

主画面で上端から失われた行を、属性・プロンプト位置・継続情報付きで履歴へ移す。リサイズでは全角・結合セルを分割せず、論理行とカーソル位置を再配置する。代替画面の出力を通常履歴へ混入させない。

OSC 133と既存のシェル通知、タイトル、既定無効のOSC 52、ファイル要求、クリアAPIを維持する。制御文字列・入力・通知の既存のサイズ上限を維持し、未知の列でパーサー状態が壊れないようにする。

## 入力遅延

原因調査では、Emacs側の20ms描画タイマー、セルごとのバッファ挿入・フォント情報取得、およびDLL側の通知後8ms待ちによる遅延を確認した。これらの削減は独自エンジン移行でも保持する。出力イベントまたは入力キューによってワーカーを起こし、アイドル時にポーリングでCPUを消費しない。

既存GUI経路を通すtests/benchmark-input.elを使用する。通常PowerShellで同じ入力列を測定し、通知受信、バッファ更新、redisplayの時間を区別する。物理キーの配送時間と画面の走査時間を含まないことを明記する。大量出力中の入力・終了・リサイズも検証する。

調査中の修正でPowerShellの中央値約8.6msを一度測定した。これは移行前の予備値であり、Windows Terminalと同等の体感や独自エンジンの性能を確認した値ではない。移行後、同じ条件で複数回測定し、現行の改善版より遅くしない。最終的な入力感はユーザーの普段の設定と実際のキー操作で確認する。

## 代替案と判断

Windows Console APIから画面を読み取る方式も考えられるが、現在の履歴・折り返し・代替画面・Unicodeの状態を同じ形で維持できることは未確認。今回の移行方式には採用しない。他のVTライブラリへの置き換えも、独自エンジンという意図を満たさないため採用しない。

## 検証と完了条件

1. 独自エンジンの単体テストで分割UTF-8/VT、セル属性、カーソル、編集、モード、履歴、reflow、キー、マウスを検証する。既存libvterm固有テストは利用者から見える契約を検証するテストへ移行する。
2. 既存のCLI統合、ERT、DLL統合、Unicodeピクセル幅などのGUI検証を維持する。PowerShell、cmd、Git Bashと検証用CLIを実際のEmacsから操作し、入力・コピー・リサイズ・終了を確認する。Vimを起動しない。
3. libvtermヘッダー、ソース、リンク対象、ランタイム依存を製品から除去する。配布DLLを再ビルドし、READMEとライセンス記載を更新する。過去の設計文書は履歴として残す。
4. 入力遅延を同じGUI経路で複数回測定し、大量出力で履歴末尾・入力・終了が失われないことを確認する。
5. 未対応のVT機能や実環境で未確認の入力感は具体的に明示し、検証していない完全互換を主張しない。

調査時点では標準ConPTYでのVim Unicode保存がUTF-8デコードエラーになり、単独再実行でも再現した。同梱ConPTYでのVim保存を含むDLL統合20件と既存GUI検証は成功した。固定8ms待ち除去後、同梱ConPTYのVimリサイズ保存も一度タイムアウトし、変更せずに全DLL統合テストを再実行すると20件すべて通過した。この不安定性も未解決の確認項目として保持し、移行後の差分と区別する。全CLI40件の合格やVim経路の安定性を確認済みとは扱わない。

## 現在の状態

承認されたイベント駆動の差分通信構成と独自エンジンを実装し、libvtermを製品入力から除去した。最終ビルドでCLI40件、ERT48件、DLL統合20件、GUI検証が成功した。現在の検証はVimを起動せず、実際のEmacsのキーマップから入力・コピー・リサイズを確認する。GUI版EmacsとPowerShellの入力からredisplayまでの中央値は3回で8.42、8.85、8.00ms。物理キーの配送と画面走査は含まない。Smart Brainの保存先projectが未指定のため、同ストアへの保存は保留している。
